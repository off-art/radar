# План реализации

Подробности к [ROADMAP.md](../ROADMAP.md): как делаем, как проверяем, чем рискуем. Размеры: S ≈ день, M ≈ 2–3 дня, L ≈ неделя+.

## Принцип работы над каждой фичей
1. Ветка `feat/<имя>`, одна фича — один PR/коммит-серия.
2. Код + юнит-тесты (`cargo test`) + проверка в tmux на демо-агентах (`/tmp/t`-стенд, сценарии ниже).
3. Обновить README (раздел, клавиши, настройки), справку `?`, палитру команд и пример `config.toml`.
4. Релиз версии: поднять `version` в `Cargo.toml`, обновить скриншоты в `docs/`, тег `vX.Y.Z`, проверить `curl … | bash` на чистой машине.

Определение готовности: тесты зелёные, фича доступна **и мышью, и клавишей, и из палитры**, описана в README, не ломает восстановление агентов.

### Шаг 1. Git в списке и шапке (S) — `src/git.rs` — ✅ сделано
- `git::Info { branch, ahead, behind, added, removed, files, dirty }`.
- Фоновый поток опрашивает `cwd` агентов раз в 3 с и сразу при переходе `работает → готов`: `git status --porcelain=v2 -b` + `git diff HEAD --shortstat`; таймаут 2 с, `GIT_OPTIONAL_LOCKS=0`; не git-папка → `None`.
- `Msg::Git(session_id, Info)` → поле `Session.git`; в списке вторая строка `Claude Code · работает · feat/x +12 −3`, в шапке — ветка и `●` при изменениях.
- Тесты: временный репозиторий (чистый, изменённый, untracked, detached HEAD, не репозиторий).
- Риск: огромные репозитории → ограничить частоту и размер вывода.

### Шаг 2. Просмотр diff (M) — `src/diff.rs`, `Mode::Diff` — ✅ сделано
- `Ctrl+b v` / ПКМ → «Изменения»: слева список файлов (`M`, `A`, `D`, `?` + `+/−`), справа дифф; `j/k` строка, `n/p` файл, `Tab` панель, `PgUp/PgDn`, колесо, `Esc`.
- Источник: `git diff HEAD --no-color -U3` + untracked через `git ls-files -o --exclude-standard` (показывать как добавленные).
- Парсер unified diff → строки типов `add / del / hunk / ctx / meta`; цвета из темы (`green`, `red`, `blue`).
- Тесты: парсер (переименование, бинарные файлы, «No newline», пустой дифф). Ограничение: файлы > 1 МБ — «слишком большой».
- Готово, когда: дифф открывается для агента с изменениями за < 300 мс на репозитории среднего размера.

### Шаг 3. Действия с git (M) ✅
- Пункты меню и палитры: «Закоммитить…» (поле сообщения; подсказка — последний промпт агента), «Отправить (push)», «Удалить worktree», «Влить ветку в основную».
- Команды выполняются в фоне; `GIT_TERMINAL_PROMPT=0`, stdin = null; результат — toast + запись в журнал событий.
- Опасные действия (удаление worktree, merge) — через существующий диалог подтверждения с описанием, что именно будет сделано.
- Тесты: сценарии на временных репозиториях (commit, worktree remove, merge без конфликта и с конфликтом → понятная ошибка).
- Риск: push требует учётных данных → показываем текст ошибки git, ничего не зависает.

### Шаг 4. Лента событий (S) — `Mode::Log` ✅
- `events: VecDeque<Event { время, агент, тип, текст }>` (до 200): «закончил за 4:12», «ждал ответа 3 мин», «запущен», «завершён (код)», результаты git-действий.
- `Ctrl+b l` / палитра; `Enter` — перейти к агенту. Бейдж в статус-строке, если есть непросмотренное.
- Не сохраняется между запусками (позже — по желанию).

### Шаг 5. Подтверждение разрешений из списка (S–M) ✅
- Действие `approve` (`y` в режиме навигации, пункт меню у агента в статусе «ждёт ответа»).
- Всегда показывает диалог с текстом запроса (`note`, например «Bash: rm -rf build») — **вслепую ничего не подтверждаем**.
- Клавиши ответа — настраиваемые для каждого агента (Claude: Enter/`1`; Codex: `y`); по умолчанию включено только для Claude (точный `note` из хука).
- Риск: ошибка в определении запроса = подтверждено лишнее → поэтому диалог обязателен, без «подтвердить всё».

## v0.4 — «Управление» (≈ 2 недели)
1. **`radar ctl`** (M): отдельный сокет `radar-ctl-<pid>.sock` + файл-реестр `~/.config/radar/instances/<pid>`; протокол — JSON-строки; команды `list`, `new <агент> <папка>`, `send <id> <текст>`, `status <id>`, `wait <id> [--for ready]`, `close <id>`, `--json`. Тесты: клиент ↔ сервер в одном процессе.
2. **Группы/проекты** (M): группа = папка/репозиторий, сворачивание, счётчик статусов группы; сохраняется в `sessions.toml`.
3. **Пресеты запуска** (S): `[[preset]]` в конфиге (список агентов + промпт) → `radar preset review`; строится на `ctl`.
4. **Токены и стоимость** (M): для Claude — читать `transcript_path` из хуков (usage по сообщениям), показывать в шапке; для остальных — «нет данных».
5. **Хуки событий** (S): `[[on]] event="ready" run="…"` — выполнить команду (в т. ч. отправить в Telegram/Slack через curl).

## v0.5 — «Живучесть» (≈ 3 недели)
Архитектура фоновых сессий:
- **Сервер** (`radar server`, запускается автоматически) держит `Session`/pty/vt100 и сокет; **клиент** — текущий интерфейс.
- Протокол: клиент → сервер: ввод, resize, команды; сервер → клиент: снимок экрана (`contents_formatted`) при подключении + поток новых байт pty; клиент держит свой `vt100::Parser`.
- Этапы: (1) вынести `Session` и хуки из `app.rs` в модуль без зависимости от UI; (2) сервер + протокол + `radar attach`; (3) автозапуск сервера, `Ctrl+b d` — отсоединиться; (4) миграция восстановления списка (`sessions.toml`) на сервер; (5) планировщик `[[schedule]]` поверх сервера.
- Риски: сложность resize при нескольких клиентах (v0.5 — один клиент), совместимость версий клиента и сервера (версия в рукопожатии).
- Критерий: закрыть окно терминала → агент продолжает работу → `radar` подключается и видит прежний экран и прокрутку.

## Риски и допущения
- Хуки Codex и GigaCode сделаны по документации; шаг 0 может потребовать правок.
- На macOS нельзя `cp` поверх работающего бинарника — только пересоздавать файл (учтено в `install.sh`).
- Тесты, зависящие от macOS (уведомления, `codesign`), выполняются только в CI; локально проверяем в tmux на Linux/macOS.
- Все новые клавиши — через `Action` и конфиг `[keys]`, чтобы не ломать пользовательские настройки.
